# NOTES.md — Design decisions

For each important decision, record what we chose, what else we considered, and why.

| Date | Decision | Alternatives considered | Why |
|---|---|---|---|
| | FastAPI + httpx (async) for the gateway | Flask, Django | Async I/O suits many concurrent LLM calls; built-in docs at /docs |
| | Build LRU cache, token bucket and circuit breaker myself | Use existing libraries | Interview preparation: must understand and explain them |
| 2026-11-14 | Cost = tokens × list price per 1M tokens, separate input/output prices, table in `config.MODEL_PRICES` | Use the provider's billed amount; one flat price per model | Providers don't return a cost; output costs more than input; free-tier calls still show what paid traffic would cost |
| 2026-11-14 | Unknown model price is stored as NULL and counted in `unpriced_requests` | Store 0 | 0 would make an unpriced model look free and hide a missing price |
| 2026-11-14 | Clients authenticate with `X-API-Key`; only SHA-256 hashes kept, a 16-char hash prefix is the client id | JWT / OAuth; store raw keys | Simple for server-to-server use; a raw key never appears in memory dumps, limits or logs. No keys configured = every `/chat` gets 401 (fail closed) |
| 2026-11-14 | Rate limit runs after auth, before the router | Limit by IP; limit before auth | Bad keys can't use up a real client's limit; limited requests never reach a provider |
| 2026-11-14 | Token bucket (default) vs sliding window log, picked by `RATE_LIMIT_ALGORITHM` | Fixed window counter; sliding window counter (weighted) | **Token bucket:** 2 numbers per client, allows a burst of `capacity` then a steady `refill` rate; good for bursty chat apps. **Sliding window log:** exact "max N in any T seconds", no double burst at a window edge (fixed window allows 2N), but stores one timestamp per request (memory ∝ limit). Fixed window rejected for the edge burst; weighted counter is a later option if limits get large |
| 2026-11-14 | Burst behaviour (defaults): token bucket lets 10 requests through at once, then 1 every 5 s; sliding window lets 12 at once, then nothing until the oldest is 60 s old | — | Both average 12/min; the bucket recovers smoothly, the window recovers in steps |
| 2026-11-14 | Redis state via one Lua script per check; Redis server `TIME` as the clock; keys expire when idle | `WATCH`/`MULTI` transactions; each gateway's own clock | A script runs atomically, so instances can't race (no lost updates); one shared clock avoids drift between instances; `PEXPIRE` stops idle clients filling Redis |
| 2026-11-14 | If Redis can't be reached the limiter fails open (allows, logs a warning), then skips Redis for 5 s; no client-side Redis retries; script errors still raise | Fail closed (reject all); keep retrying Redis on every request | A limiter outage shouldn't become a full gateway outage, and requests shouldn't each wait on a dead Redis. Only connection/timeout errors fail open, so a script bug can't silently switch limiting off. Revisit if abuse matters more than availability |
| 2026-11-14 | `Retry-After` = seconds rounded up, at least 1; `X-RateLimit-Remaining` on every answer | Float seconds; HTTP date | The header must be whole seconds; rounding down could send clients back too early |
| 2026-11-14 | Exact cache = my own LRU + TTL (dict + doubly linked list), or Redis `SET ... PX` when `REDIS_URL` is set | `functools.lru_cache`, `OrderedDict`, cachetools | O(1) get/set/evict; lazy expiry (no cleanup thread). Redis version is shared by every instance and fails open (miss) if Redis is down |
| 2026-11-14 | Exact key = SHA-256 of the prompt with whitespace collapsed; case kept | Raw prompt as key; lowercase too | Short fixed-size keys, prompts never stored as key names; "US" vs "us" can differ in meaning |
| 2026-11-14 | Cache is shared across all client keys | One cache per client | Higher hit rate; fine while all clients are mine. Per-tenant caches needed if clients must not see each other's answers |
| 2026-11-14 | Only answers that finished normally are cached (Groq `stop`, Gemini `STOP`); cut-off or filtered ones (`length`, `MAX_TOKENS`, `SAFETY`, ...) are returned but not cached | Treat as error; block only `MAX_TOKENS` | The client still gets something, but a broken answer is never replayed to others. An allowlist is safer than listing every bad reason |
| 2026-11-14 | Order: exact cache, then semantic cache, then providers; both caches filled on a miss | Semantic only | Exact lookup is a hash (µs) and needs no embedding; semantic costs ~10 ms of CPU |
| 2026-11-14 | Semantic cache = numpy matrix, linear scan (one matrix multiply); new entries use an empty/expired slot, else overwrite the oldest; one embedding at a time (async lock) | FAISS / HNSW index; Redis vector search; parallel embedding threads | 1000 × 384 floats is ~1.5 MB and one multiply; an ANN index is the step for millions of entries. The tokenizer isn't thread-safe and parallel CPU embeddings only compete for cores |
| 2026-11-14 | Semantic cache off by default, threshold 0.94 | 0.90 (common default) | Measured on 123 pairs (eval/results.md): at 0.90, 78% hit on paraphrases but 33% false hits on look-alike questions; at 0.94, 60% / 22%. Swapped-direction questions ("miles to km" vs "km to miles") score 0.99+, so no threshold alone is safe |
| 2026-11-14 | Cache hits logged as rows with status `cache_exact` / `cache_semantic`, 0 tokens, $0, and `saved_usd` = original cost | Separate cache table; counters in memory | `/stats` hit rate and money saved come from the same table as everything else and survive restarts |
| 2026-11-14 | Redis exact cache: after any Redis error, skip Redis for 5 s (all lookups miss) | Retry Redis on every request | A hung Redis would otherwise add up to 2 × 0.5 s timeout to every request |
| 2026-11-14 | Guard before every semantic hit: same numbers (digits, number words, ordinals), same negation, same word after to/into/from/than/vs; if the best match fails, try the next best | Higher threshold only; cross-encoder re-check; LLM judge | Threshold alone can't separate "5 miles to km" from "5 km to miles" (0.99). Word rules cost microseconds and need no model. At 0.94: false hits 22% → 3% (hold-out set 40% → 7%) with the same hit rate. Misses antonyms and swapped numbers; a cross-encoder is the next step if that matters |
| 2026-11-14 | Guard features (numbers, negation, directions) computed once when an entry is stored and once per lookup; prompts capped at `MAX_PROMPT_CHARS` (32000, else 422) | Re-tokenise both prompts for every candidate; no length cap | A 50k-word prompt took ~24 s in the old guard and blocked the event loop; now linear and checked once |
| 2026-11-14 | Dedup: map of in-flight `asyncio.Task`s keyed by the exact-cache key; first request starts the call, the rest await the same task through `asyncio.shield`; key removed when the task finishes | Hold a lock per key and re-check the cache; Redis lock across instances | Followers get the answer the moment it arrives, without waiting on a lock and a second cache read. Shield means one client hanging up doesn't cancel the call for 49 others. Per process only: two instances can each make one call for the same prompt (a Redis lock + pub/sub would fix that, at the cost of a round-trip on every miss) |
| 2026-11-14 | Dedup runs after both caches miss, and the cache is filled inside the shared call | Dedup before the cache lookup | Cache hits stay a fast path. Filling the cache before the key is removed means a request arriving just after the call finds the answer in the cache |
| 2026-11-14 | Errors are shared too: if all providers fail, every waiting request gets the same 503 | Let followers retry on their own | 50 followers each retrying a failing provider is exactly the thundering herd dedup is meant to stop (test: 10 waiters → 3 provider calls, not 30) |
| 2026-11-14 | Shared requests logged with status `dedup`, 0 tokens, `saved_usd` = the call's cost; counted as `deduplicated` in `/stats`, not as cache hits | Count them as cache hits | They never touched the cache, so mixing them in would inflate the cache hit rate; the money saved is still included in `saved_usd` |
| 2026-11-14 | Consistent hash ring: MD5 → 64-bit positions, 100 virtual nodes per node, sorted list + binary search | `hash(key) % N`; rendezvous (highest random weight) hashing; jump hash | `% N` moves ~75% of keys when going 3 → 4 nodes, the ring moves 24% (ideal 25%), and only onto the new node. Python's `hash()` is randomised per process, so MD5 keeps every instance agreeing. 100 virtual nodes keep the busiest of 4 nodes at ~29% of keys (1 virtual node: 41%). Rendezvous is simpler but O(N) per lookup; jump hash can't remove an arbitrary node |
| 2026-11-14 | Sharded exact cache only when `CACHE_NODES` lists 2+ Redis URLs; keys that move just miss once and are refilled | Copy moved keys to their new node | It's a cache: a miss costs one provider call, so a migration step isn't worth the complexity |
| 2026-11-14 | Dashboard time series built on demand from the `requests` table (`GET /stats/timeseries`), buckets filled in Python, latency p50/p95 by nearest rank | Pre-aggregated per-minute table; Prometheus + Grafana; percentiles in SQL | One source of truth, no extra service. SQLite has no percentile function. Fine for thousands of rows; a rollup table (or Prometheus histograms) is the step for millions |
| 2026-11-14 | Latency percentiles count only `ok` rows (real provider answers) | Include cache hits and failed attempts | Cache hits (~1 ms) would drag p50 down and hide provider slowness; failed attempts are not answers. The request chart still shows hits and failures |
| 2026-11-14 | Dashboard polls every 5 s through the Vite dev proxy | WebSocket / Server-Sent Events push; CORS on the gateway | Polling is simple and 5 s is fresh enough for a dashboard; the proxy means the gateway needs no CORS setup |
| 2026-11-14 | Money saved measured by replaying a synthetic 300-request mix (30 popular questions with Zipf popularity and 3 wordings, 8 look-alikes, 30 one-offs) against real Groq, one request at a time | Replay a public chat log (e.g. LMSYS); only report the false-hit eval | No real users yet, and public chat logs are mostly unique long prompts (hits would say little about an FAQ-style app). A Zipf mix is the usual shape of repeated traffic; the README says it's synthetic and the hit rate depends on how repetitive traffic is. Sequential so dedup doesn't mix into the cache numbers |
| 2026-11-14 | Load tests use a fake provider (`PROVIDER_ORDER=fake`, fixed 300 ms, priced like gpt-oss-20b) | Load test against real Groq; mock server in a separate process | Free tiers allow a few requests per minute, so a real-provider test would only measure their rate limit. In-process fake keeps the gateway code path identical and costs nothing |
| 2026-11-14 | SQLite in WAL mode with `synchronous=NORMAL` | Default rollback journal; log in a background thread or batch inserts; move to PostgreSQL | Each commit waited ~10 ms for the disk on the event loop: 64 req/s, p50 670 ms with a 300 ms provider. WAL: 0.09 ms per insert, 128 req/s, p50 300 ms. Risk: a power cut can lose the last few log rows (not an app crash). A log writer queue is the next step if logging shows up again |
| 2026-11-14 | Semantic embeddings micro-batched: prompts that queue while one model call runs go together in the next call (max 32), still one call at a time | One at a time (async lock); fixed wait window to fill a batch; several threads | 17.6 ms per prompt alone vs ~5 ms in a batch of 8+. No added wait when traffic is light. Semantic run: 137 → 378 req/s, p95 5.9 s → 1.2 s. Shutdown lets the running batch finish (cancelling it would leave the thread running and the next call could overlap it) |
| 2026-11-14 | Streaming as a separate `POST /chat/stream` (Server-Sent Events: `chunk`, `done`, `error`) | `"stream": true` flag on `/chat`; WebSockets | SSE is plain HTTP, one-way (all we need) and what OpenAI-style APIs use. A separate route keeps `/chat`'s JSON response type simple |
| 2026-11-14 | Retries, circuit breaker and fallback only before the first streamed piece; after that a provider error becomes an `error` event | Restart the answer on the backup provider | The client already has part of one model's answer; switching would glue two different answers together. A mid-answer failure still counts against the provider's breaker (only while CLOSED, so a late result can't reopen it) |
| 2026-11-14 | Gateway waits for the first piece before replying | Start the 200 stream straight away | If every provider fails the client gets a normal 503, not a 200 stream that breaks at once |
| 2026-11-14 | Cache hits sent as one piece; complete streamed answers stored in both caches; streams skip dedup | Fake word-by-word replay of cached answers; share one stream between identical requests | Replaying slowly only adds latency. Sharing a live stream needs a fan-out buffer per prompt; left for later |
| 2026-11-14 | Client hanging up mid-answer: the clean-up runs in a shielded cancel scope, closes the provider's connection and logs the row as `cancelled` | No log row; log as `error` | The provider may still bill those tokens, and a disconnect isn't the provider's fault, so it mustn't count as an error or against the breaker |
